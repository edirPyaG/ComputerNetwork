# RDT 协议优化总结：NewReno + SACK 实现

## 1. 概述
本文档总结了对可靠数据传输 (RDT) 协议实现的关键错误修复和算法改进。目标是建立一个健壮且高性能的传输协议，能够在丢包（如 3%）和延迟（如 5ms）环境下稳定工作，而不会陷入超时死锁循环或吞吐量崩溃。

## 2. 发现的关键问题
在模拟丢包环境（路由器 3% 丢包，5ms 延迟）测试期间，初始实现表现出以下严重问题：
1.  **“全员超时”死锁**：发送方会进入连续超时的状态，导致拥塞窗口 (`cwnd`) 塌缩为 1，吞吐量实际上降为零。
2.  **NewReno 逻辑错误**：算法未能正确处理部分确认 (Partial ACK)，将其视为普通 ACK 或忽略，导致无法在单个窗口内从多次且连续的丢包中快速恢复。
3.  **违反 RFC 6298（“多米诺骨牌”效应）**：当数据包因超时而重传时，后续缓冲数据包的计时器没有被重置。结果是，后续数据包一旦到达队列前种种，就会立即“超时”，导致一连串的错误超时判定。
4.  **握手阻塞**：三次握手使用阻塞 I/O 实现且无重传机制，导致如果初始 SYN 包丢失，发送方将无限挂起。
5.  **性能瓶颈**：过多的控制台日志输出和简单的 Pacing（休眠）策略严重限制了无损耗条件下的吞吐量。

## 3. 已实施的解决方案

### 3.1. 算法修复 (NewReno + SACK)
*   **NewReno 部分确认 (Partial ACK) 支持**：
    *   引入了 `recover` 变量，用于标记进入快速恢复模式时发送的最高序列号。
    *   修改了 ACK 处理逻辑：如果在 `in_fast_recovery` 期间收到新的 ACK 但 ACK 小于 `recover`（即 Partial ACK），发送方**保持在快速恢复状态**并**立即重传**下一个丢失的报文。这允许在一个 RTT 内恢复多个丢失的数据包，而无需等待超时。
*   **快速重传阈值调整**：
    *   将重复 ACK (Duplicate ACK) 阈值从 **3 降低到 2**。在小窗口场景（拥塞期间很常见）中，往往无法收到 3 个重复 ACK。降低此阈值使协议对丢包更加敏感，触发快速重传而不是回退到缓慢的超时重传。
*   **拥塞窗口动态调整**：
    *   **超时恢复**：不再将 `cwnd` 重置为 `1 * MSS`（这会导致流水线饥饿），而是重置为 `4 * MSS`。这确保了有足够的数据包在飞行中，以便在发生进一步丢包时有潜力触发重复 ACK。

### 3.2. 关键逻辑修复 (计时器管理)
*   **RFC 6298 计时器重启（修复“多米诺”效应）**：
    *   **收到新 ACK 时**：当数据包被确认并从缓冲区移除时，*新*队首数据包的 `time_sent` 会被重置为当前时间。
    *   **发生超时时**：当发生超时时，**所有**当前缓冲数据包的 `time_sent` 都会被重置为当前时间。这彻底消除了错误超时的级联反应。

### 3.3. 健壮性与性能
*   **非阻塞握手**：将阻塞的 `recvfrom` 替换为基于 `select()` 的带超时循环。如果在 `TIMEOUT_MS` 内未收到 SYN-ACK，则自动重传 SYN 包。
*   **移除 Pacing**：移除了硬编码的每包 `500us` 休眠，允许发送方利用全部可用带宽。
*   **优化等待**：在流控制循环中用 `this_thread::yield()` 替换了 `sleep_for(1ms)`，以减少等待窗口空间时的延迟。
*   **日志抑制**：注释掉了高频日志（如每包超时/重传消息），防止 I/O 阻塞干扰 RTT 感知。

## 4. 配置调优
*   **超时时间 (RTO)**：将 `TIMEOUT_MS` 调整为 **300ms**。该值足够大以吸收系统抖动和 Windows 调度延迟，同时也足够小以对真正的网络中断做出合理反应。

## 5. 结果
协议现在可以在有损链路（3% 丢包，5ms 延迟）上成功完成大文件传输，并具有以下特征：
*   **零死锁**：发送方能够利用快速重传（重复 ACK）和 Partial ACK 有效地从丢包中恢复。
*   **统计数据正确**：
    *   重传数据包：约 100 个（符合约 1800 个数据包 + 重传的 3% 丢包率预期）。
    *   超时：显著减少（仅在快速重传失败时发生）。
    *   吞吐量：稳定且功能正常（取决于具体的丢包模式和 RTT，约 0.1 - 0.7 Mbps），远优于之前的“卡死”状态。
