\begin{abstract}
    本实验旨在深入研究用户态 Rootkit 的持久化机制与隐蔽技术，选取了具有代表性的开源工具 r77 作为研究对象。r77 采用“反射式 DLL 注入”与“API Hooking”相结合的技术路径，在不触及 Windows 内核（Ring 0）的情况下，实现了对系统进程、文件系统、注册表及网络连接的全方位隐藏。实验中，我首先构建了包含目标靶机与监控套件的测试环境，完整复现了 r77 的植入与隐藏过程。利用 Process Explorer、TCPView 等专业取证工具，我对比了 Rootkit 开启前后的系统状态，证实了其针对 \texttt{NtQuerySystemInformation} 等关键原生 API 的拦截效果。

    更进一步，本报告详细剖析了其底层的 Detours Hook 机制，解释了恶意代码如何通过修改函数入口指令（Trampoline 技术）来劫持执行流并篡改返回的结构体数据（如 \texttt{SYSTEM\_PROCESS\_INFORMATION} 链表）。实验结果表明，尽管用户态 Rootkit 无法逃避内核级检测，但其对常规系统管理工具的欺骗性极强。通过本次实践，我不仅掌握了恶意代码的隐藏原理，也为后续研究基于内存取证的检测方法积累了实战经验。

\end{abstract}

\section{实验概述}

\subsection{实验目的}
\begin{enumerate}
    \item \textbf{深入理解 Rootkit 隐蔽机制}：从系统调用（Syscall）与用户态 API 交互的层面，剖析 Rootkit 如何通过“中间人”攻击的方式篡改系统视图，区分 Ring 3（用户态）与 Ring 0（内核态）隐藏技术的本质差异。
    \item \textbf{验证 r77 框架的攻击效能}：在受控环境中部署 r77，针对进程、文件、注册表及网络端口实施隐藏操作，评估其对抗任务管理器（TaskMgr）、资源管理器（Explorer）及网络状态工具（Netstat）的能力。
    \item \textbf{掌握 Hook 技术核心原理}：通过分析 Detours 库在 r77 中的具体实现，掌握 Inline Hook 的指令级流程，包括指令重写、Trampoline 构造及负载函数的过滤逻辑。
\end{enumerate}

\section{实验原理}

\subsection{用户态 Rootkit 与内核态 Rootkit 的辨析}
Rootkit 的核心目标是维持对系统的持久化控制并隐藏自身踪迹。
\begin{itemize}
    \item \textbf{内核态 Rootkit (Ring 0)}：通常以驱动程序（.sys）形式存在，直接修改内核结构（如 SSDT、IDT）或操纵内核对象（DKOM）。其权限最高，隐藏最彻底，但开发难度大，且容易触发 PatchGuard 导致蓝屏。
    \item \textbf{用户态 Rootkit (Ring 3)}：如 r77，运行在用户空间。它不修改内核，而是通过注入到每一个用户进程中，拦截这些进程对系统的查询请求。其稳定性好，兼容性强，但无法欺骗运行在内核层的安全软件（如 EDR 的内核探针）。
\end{itemize}

\subsection{r77 的核心注入机制：Reflective DLL Injection}
r77 实现了“无文件”攻击的一个变种。虽然它可能在磁盘上有配置文件，但其核心恶意代码（Payload DLL）主要通过 \textbf{Reflective DLL Injection（反射式 DLL 注入）} 技术加载。
传统的 DLL 注入依赖 Windows API \texttt{LoadLibrary}，这会使 DLL 模块出现在 PEB（进程环境块）的模块列表中，极易被检测。而反射式注入则是将 DLL 作为一段原始数据写入目标进程内存，通过一段自举的 Shellcode 手动解析 PE 头、修复重定位表和导入表，并在内存中直接执行 \texttt{DllMain}。这意味着 r77 的 DLL 不会注册在系统的模块链表中，从而实现了“隐形加载”。

\subsection{基于 Detours 的 API Hooking 与数据过滤}
r77 的隐藏逻辑完全依赖于对 Windows Native API 的拦截。相较于高层的 Win32 API（如 \texttt{Process32First}），Hook 底层的 Native API（如 \texttt{ntdll.dll} 中的函数）能覆盖更广泛的调用场景。

以 **进程隐藏** 为例，其技术细节如下：
\begin{enumerate}
    \item \textbf{拦截目标}：\texttt{NtQuerySystemInformation}，这是所有系统监控工具（包括 TaskMgr）获取进程列表的必经之路。
    \item \textbf{原始调用}：Hook 函数首先调用原始的 API，获取真实的系统快照。此时，内存中存在一个 \texttt{SYSTEM\_PROCESS\_INFORMATION} 类型的结构体链表。
    \item \textbf{链表遍历}：Hook 遍历该链表，检查每个节点的 \texttt{ImageName} 字段。
    \item \textbf{节点摘除}：一旦发现进程名以 \texttt{\$77} 开头，Hook 函数修改 **前一个节点** 的 \texttt{NextEntryOffset} 指针，使其跳过当前恶意节点，直接指向 **后一个节点**。
    \item \textbf{返回结果}：将修改后的链表返回给调用者。由于链表中不再包含恶意进程节点，工具自然无法显示。
\end{enumerate}

\subsection{r77 环境部署与初始化}
首先，我将 r77 的安装包传输至虚拟机中。解压后可以看到其目录结构简洁，包含 \texttt{Install.exe}（安装/注入器）、\texttt{Uninstall.exe} 以及一个用于验证效果的 \texttt{TestConsole.exe}。

\textbf{操作分析}：运行 \texttt{Install.exe} 时，它实际上执行了一个全局注入操作。它不仅将 DLL 注入当前运行的所有进程，还会注册一个计划任务或修改注册表 AppInit\_DLLs（具体取决于配置），以确保系统重启后新创建的进程也会被自动注入。这是一种典型的 \textbf{持久化（Persistence）} 行为。

\subsubsection{隐藏前}
打开任务管理器，可以明确看到名为 \texttt{\$77TestConsole.exe} 的进程，CPU 占用率高居榜首。

\subsubsection{隐藏后}
运行 \texttt{Install.exe} 激活 Rootkit。此时再观察任务管理器，出现了一个非常诡异的现象（如图 \ref{fig运行install.exe}）：
\begin{itemize}
    \item \textbf{CPU 总使用率}：依然维持在较高水平（例如 60-70\%），风扇转速未减，说明 CPU 仍在进行高强度运算。
    \item \textbf{进程列表}：\textbf{找不到} 任何高占用的进程。列表中的所有进程 CPU 占用之和远小于总占用率。所谓的“系统空闲进程”并没有占据 CPU，多出的 CPU 时间仿佛凭空消失了
\end{itemize}

\textbf{分析}：这正是用户态 Rootkit 的局限性体现。r77 虽然从应用层视图（TaskMgr 调用 \texttt{NtQuerySystemInformation} 获得的链表）中移除了恶意进程的节点，但它**无法修改内核调度器**。Windows 内核调度器（Scheduler）依然在正常地给恶意线程分配时间片，因此 CPU 实际上是在忙碌的。但由于任务管理器的显示数据来源被篡改，它无法将这部分 CPU 负载归属到具体的进程名下，从而导致了“总负载 > 各进程负载之和”的数据不一致现象。这可以作为检测 Rootkit 的一个重要特征。

\subsection{文件系统隐藏验证}
接下来验证文件隐藏功能。r77 默认配置隐藏所有以 \texttt{\$77} 为前缀的文件。

\subsubsection{实验步骤与现象}
我在测试目录下尝试创建一个名为 \texttt{\$77Secret.txt} 的文件。
\begin{itemize}
    \item \textbf{创建瞬间}：鼠标右键 -> 新建 -> 文本文件。当我输入文件名并回车确认的瞬间，\textbf{文件图标凭空消失了}。
    \item \textbf{验证存在性}：我尝试再次在该目录下创建同名文件，系统提示“文件已存在”。这证明文件确实被写入了磁盘（NTFS 文件系统中有记录），只是文件资源管理器（Explorer.exe）“看不见”它。
\end{itemize}

\textbf{原理分析}：Explorer.exe 为了显示文件列表，会调用 \texttt{NtQueryDirectoryFile}。r77 注入到 Explorer.exe 进程中的 DLL 截获了该调用，遍历返回的文件信息数组，一旦发现文件名匹配 \texttt{\$77...}，就通过修改指针偏移量（Offset）的方式将该条目从数组中剔除。因此，用户界面渲染出的列表中就不包含该文件。这种隐藏是实时的，且对所有注入了 r77 的程序（如 cmd.exe, PowerShell, Notepad 等）都有效。

\subsection{注册表隐藏分析}
注册表隐藏是 r77 实现自我保护的关键一环。r77 的配置信息通常保存在 \texttt{HKEY\_LOCAL\_MACHINE\textbackslash SOFTWARE\textbackslash \$77config} 等位置。若不对这些键值进行隐藏，系统管理员可通过注册表编辑器（RegEdit）轻易发现异常配置，进而追溯到 Rootkit 的存在。

\subsubsection{技术机制}
注册表隐藏的实现原理与文件隐藏类似。当注册表编辑器展开某一键节点时，Windows 会调用 \texttt{NtEnumerateKey} 或 \texttt{NtEnumerateValueKey} 等 Native API 来枚举子键和键值。r77 通过 Hook 这些函数，在返回结果前对数据进行过滤：检查返回的键名（Key Name）或值名（Value Name），若检测到 \texttt{\$77} 前缀，则从返回缓冲区中删除该项，并调整后续条目的索引以保持连续性。经此处理后，管理员在注册表编辑器中将无法察觉 Rootkit 配置项的存在，显著增加了取证和清除的难度。

\subsubsection{实验验证}

\subsubsection{根因分析}
经过深入分析，我总结出导致上述现象的技术原因如下：

r77 的注册表隐藏功能依赖于对用户态进程的 API Hook，主要拦截 \texttt{RegEnumKeyExW}、\texttt{RegOpenKeyExW}、\texttt{NtEnumerateKey} 等函数。然而，\texttt{HKEY\_CLASSES\_ROOT}（HKCR）并非一个独立的注册表 Hive，而是 \texttt{HKEY\_LOCAL\_MACHINE\textbackslash SOFTWARE\textbackslash Classes} 与 \texttt{HKEY\_CURRENT\_USER\textbackslash SOFTWARE\textbackslash Classes} 的\textbf{联合视图（Merged View）}。

由于 HKCR 的这种特殊架构，其访问路径往往会绕过用户态的 API Hook，或由系统服务（如 COM 相关服务）代理完成访问。在这些场景下，r77 注入的 Hook 无法拦截到相关调用，自然也就无法实现隐藏。

相比之下，\texttt{HKEY\_CURRENT\_USER}（HKCU）下的路径（如 \texttt{Printers}）是直接由用户态进程访问的标准 Hive。当注册表编辑器枚举这些路径时，必然调用 \texttt{NtEnumerateKey} 等 API，r77 的 Hook 能够完全生效，从而成功实现隐藏。

        \toprule

        \midrule
        \texttt{HKEY\_CLASSES\_ROOT}  & 失败            & 联合视图，访问路径可能绕过用户态 Hook \\
        \texttt{HKEY\_CURRENT\_USER}  & 成功            & 标准 Hive，API 调用可被完全拦截  \\
        \texttt{HKEY\_LOCAL\_MACHINE} & 部分成功          & 取决于具体子键的访问方式          \\

\subsubsection{结果与分析}

\textbf{技术细节}：网络工具通常调用 \texttt{GetExtendedTcpTable} (iphlpapi.dll) 来获取系统的 TCP 连接表。r77 拦截该 API，解析返回的 \texttt{MIB\_TCPTABLE} 结构。该结构包含一系列 \texttt{MIB\_TCPROW} 行，每一行代表一个连接，包含本地 IP、端口、远程 IP、端口和所属进程 PID。r77 遍历这些行，比对端口号。一旦匹配，它通过内存拷贝（Memory Copy）将后续的所有行向前移动，覆盖掉当前行，并将总行数（dwNumEntries）减一。这种直接操作内存缓冲区的技术非常底层且高效，使得上层应用完全感知不到数据的缺失。

\section{拓展阅读}

\subsection{Detours 技术概述}
Microsoft Detours 是微软研究院开发的一款用于在 Windows 上拦截二进制函数调用的库。虽然其初衷是用于调试、性能分析和热补丁（Hot Patching），但其强大的 Inline Hook 能力也常被 Rootkit 开发者利用。

在 r77 中，Detours 被用来修改内存中目标 API 的前几条指令，强行改变 CPU 的执行流（PC 指针），使其跳转到攻击者编写的 Hook Payload 中。

\subsection{Inline Hook 的实现细节}
Detours 的核心操作是对函数入口的“外科手术式”修改。其标准流程如图 \ref{fig:detours_flow} 所示：

\begin{figure}[H]
    \centering
    \setlength{\fboxsep}{6pt}
    \fbox{
        \begin{minipage}{0.9\linewidth}
            \centering
            \small
            \textbf{函数调用流程对比}\\[4pt]
            \begin{tabular}{lcl}
                \toprule
                \textbf{原始调用路径}     & $\Rightarrow$ & User Code $\rightarrow$ Original API $\rightarrow$ Return                                                                                                      \\
                \midrule
                \textbf{Hook 后调用路径} & $\Rightarrow$ & User Code $\rightarrow$ \textcolor{red}{\textbf{Trampoline (JMP)}} $\rightarrow$ \textcolor{red}{\textbf{Hook Function}} $\rightarrow$ Original API (Optional) \\
                \bottomrule
            \end{tabular}
        \end{minipage}
    }
    \caption{Detours 函数拦截流程模型}
    \label{fig:detours_flow}
\end{figure}

具体步骤如下：
\begin{enumerate}
    \item \textbf{Trampoline 创建}：Detours 首先会申请一段内存（Trampoline），将目标函数（Target Function）开头被覆盖的指令（通常是 5 字节以上）复制到这里，并在末尾添加一条跳回原函数剩余部分的 JMP 指令。
    \item \textbf{覆写入口（Rewriting Target）}：目标函数的入口地址被修改为一条无条件跳转指令（\texttt{JMP rel32}），目标地址指向 Hook 函数。
    \item \textbf{执行 Hook 逻辑}：当程序调用 API 时，首先跳转到 Hook 函数。在此处，r77 编写的代码会执行数据过滤（如遍历链表删除名为 \texttt{\$77} 的节点）。
    \item \textbf{回溯（Optional）}：如果 Hook 函数需要原 API 的结果，它会调用 Trampoline，从而执行原函数的原始逻辑。
\end{enumerate}

\section{总结}

\subsection{实验成果}
本次实验围绕 r77 Rootkit 展开了全方位的分析与实践。通过在受控虚拟环境中部署这一用户态恶意软件，我系统性地验证了其在进程、文件、注册表及网络层面的隐藏能力。实验结果表明，基于 API Hooking 的隐藏技术虽然不涉及 Windows 内核的修改，但对于依赖标准 Windows API 的监控工具（如任务管理器、资源管理器、Netstat）具有极强的欺骗性。

在技术原理层面，通过深入研究 Microsoft Detours 机制，我理解了 Inline Hook 是如何通过修改函数入口指令、构造 Trampoline 跳板来实现执行流劫持的。这不仅解释了 r77 的工作方式，也为后续研究用户态 Rootkit 的检测方法提供了理论基础。

\subsection{关键发现}
在实验过程中，我获得了以下几点重要发现：

\begin{enumerate}
    \item \textbf{CPU 负载异常作为检测特征}：当 r77 隐藏高 CPU 占用进程后，任务管理器显示的"各进程 CPU 占用之和"将明显小于"系统总 CPU 占用率"。这种数据不一致现象可作为检测用户态 Rootkit 的重要线索。

    \item \textbf{注册表 Hive 架构对 Hook 有效性的影响}：通过对 \texttt{HKEY\_CLASSES\_ROOT} 与 \texttt{HKEY\_CURRENT\_USER} 的对比测试，我发现 r77 的注册表隐藏功能仅对标准 Hive 有效，而对联合视图（Merged View）类型的虚拟 Hive 无效。这一发现揭示了用户态 Rootkit 的固有局限性——其隐藏能力高度依赖于目标 API 的调用路径是否经过被 Hook 的用户态函数。

    \item \textbf{反射式 DLL 注入的隐蔽性}：r77 采用的 Reflective DLL Injection 技术使其 Payload DLL 不出现在进程的模块列表（PEB.Ldr）中，传统的模块枚举检测方法对其无效。
\end{enumerate}
